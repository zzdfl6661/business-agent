## 一、项目速览（执行前必读）

**项目**：连锁密室逃脱门店「企业经营智能决策与自动化执行 Agent」。
**闭环**：数据获取（美团 Playwright 采集）→ 数据分析（Pandas 确定性计算）→ 问题诊断 →
策略生成 → 报告（LLM）→ 自动执行（**执行计划 + 用户确认**，非直接改库）。

**技术栈**：Python 3.13 · FastAPI · LangGraph 1.2 / LangChain 1.x（Supervisor 双 Agent）·
SQLAlchemy 2 + MySQL（`business_agent` 库，37 家真实门店 / 23.3 万订单 / 896 条真实推广）·
Chroma + BM25 混合检索 RAG（99 chunks，7 份真实知识文档）· DeepSeek / CodeBuddy(workbuddy2api) 双 LLM 通道。

**重要事实（与 README 旧内容不同，以本文为准）**：
- ✅ 代码全部位于**项目根目录**，**无 `backend/` 子目录**（已于 2026-08-14 删除）。
- ✅ **无任何 Mock**：无 MockLLM、无模拟业务数据、无内置示例知识。未配置 LLM Key 时 `create_llm` 抛 `ValueError`；数据库不可用时数据工具返回明确错误。**新增功能必须走真实链路。**
- ✅ 已有 API Token 鉴权（`BIZ_API_TOKEN`，见 `config/auth.py`）与执行计划授权机制（`tools/execution_plans.py`）。
- 运行目录：向量库 `chroma_db/`、日志 `logs/` 均在根目录（`.gitignore` 已忽略）。
- `.env` 含真实密钥（MySQL 密码 / DeepSeek Key / stores.json 路径），**严禁提交**。

## 三、待办问题清单

> 优先级：**P0**=安全/数据正确性，**P1**=质量/体验，**P2**=工程化。
> 原建议编号 #1–#15 中：#1、#4 已完成；#10（Mock 数据脱节）已随 Mock 删除一并解决（仅需清理 docs 残留描述）。

### #2 【P0】知识上传接口安全（路径穿越 + 幂等粒度错误）
- **位置**：`api/chat.py::rag_upload`
- **问题**：
  1. `dest = loader.DATA_DIR / filename` 直接拼接上传文件名 → **路径穿越风险**（`filename="../../x"`）；
  2. 无文件大小/类型限制，可打满磁盘；
  3. 幂等删除按 `doc_type` 清库——上传未匹配 `DOC_TYPE_MAP` 的文档（doc_type=`general`）会**清空所有 general 文档**（含此前上传的其他文档）。
- **建议**：文件名取 basename + 白名单后缀（md/txt/pdf/docx）；限制大小（如 20MB）；幂等删除改为**按 `source`（文件名）**而非 doc_type；上传前校验内容非空。
- **涉及**：`api/chat.py`、`rag/loader.py`（可新增 `upload_and_ingest` 专用函数）。

### #3 【P0】经验层同日报告互相覆盖
- **位置**：`agent/nodes.py::_ingest_report_to_kb`
- **问题**：幂等逻辑 `client.delete("report", report_date=today)`——同一天**不同门店/不同问题**生成的多份报告互相覆盖，只留最后一份。
- **建议**：删除粒度改为 `report_date + store_id`（或 + 问题哈希），并给 report 文档加 `report_id` 唯一标识；检索端过滤同步。
- **涉及**：`agent/nodes.py`、`rag/retriever.py`。

### #5 【P1】"流式"是模拟的，首 token 延迟 = 全量生成时间
- **位置**：`api/chat.py::chat_stream`
- **问题**：`stream_mode="updates"`（节点级）不透传子图内 LLM token，报告生成完才按 6 字/帧模拟打字机；且 `input_tokens/output_tokens` 两个变量**从未被真实更新**，usage 靠 `report_chars×12/×3` 粗估。
- **建议**：用 LangGraph 1.x `astream_events` 透传子图内 LLM chunk（真流式）；至少做好"生成中"状态（现在 8s 生成期用户看不到输出）；usage 用 `on_chat_model_end` 事件采集真实 token。
- **涉及**：`api/chat.py`。

### #6 【P1】意图路由关键词穷举（扩展性瓶颈 + 判定不一致）
- **位置**：`agent/nodes.py`（`DATA_KEYS` / `KNOWLEDGE_KEYS` / `market_keys` 三处独立词表）
- **问题**：① 门店/指标词无法穷举；② 双列表命中冲突（如"报销流程数据"同时命中知识词"报销"和数据词"数据"）；③ supervisor 与 report 的判定逻辑不同步。
- **建议**：① 收敛为**一份统一路由配置**，supervisor 与 report 共用同一判定函数；② 增加**门店名 → store_id 解析**（`data/stores.json` 的 `search_keyword` 已具备，做模糊匹配工具，解决"XX店营业额"高频问题——现在 LLM 只能猜 store_id=1）；③ 中期升级"关键词初筛 + embedding 二判"兜底。
- **涉及**：`agent/nodes.py`、`agent/graph.py`、新增门店解析工具。

### #7 【P1】查询无缓存、LLM 实例重复创建、kb 检索串行
- **位置**：`tools/database_tool.py`、`config/llm_factory.py`、`agent/nodes.py::rag_node`
- **问题**：① 每请求实时聚合近 7 天 23.3 万订单（无缓存）；② `create_llm()` 每次调用新建实例；③ kb 链路 4 路检索（原问题+改写×2+HyDE）**串行**执行。
- **建议**：① 数据工具结果加 TTL 缓存（内存或 Redis，`/api/workflow/refresh` 成功后失效）；② `create_llm` 按 provider 缓存复用；③ kb 多路检索用 `asyncio.gather` 并行。
- **涉及**：`tools/database_tool.py`、`config/llm_factory.py`、`agent/nodes.py`。

### #8 【P1】可观测性不足
- **位置**：`api/chat.py`、`config/logging_setup.py`、`agent/nodes.py`、`tools/`
- **问题**：① 多处 `except Exception: pass` 吞异常；② 审计只有文件/表写入，**无查询接口**（运营者无法查"谁做了什么"）；③ SSE 出错只发 error 事件，无状态码/重连协议；④ 工具失败 `str(exc)` 可能含 SQL 细节直接暴露给 LLM/前端。
- **建议**：① request_id 贯穿全链路（日志 + 审计 + 前端 trace）；② `GET /api/audit` 只读查询接口（按时间/事件类型/会话过滤）；③ 工具错误信息脱敏。
- **涉及**：`api/chat.py`、`config/logging_setup.py`、`tools/`。

### #9 【P1】RAG 检索性能与存储效率
- **位置**：`rag/retriever.py::_hybrid_rerank`、`rag/loader.py::split_documents_hierarchical`
- **问题**：① BM25 每次查询都 `col.get(...)` **全量拉取整个 collection**（O(N)，知识库越大越慢，是 kb 问答 8.6s 的重要构成）；② 父子切割把 `parent_content`（上限 2500 字）**冗余存进每个子块**，存储膨胀；③ `SCORE_THRESHOLD` 注释还写"all-MiniLM 中文偏低"，与实际 bge-zh 不符。
- **建议**：① BM25 语料进程级缓存（ingest/upload 后失效）；② 父块内容抽独立 collection / id 引用，子块只存 `parent_id`，检索后回查；③ 升级 `bge-m3` 并考虑加 **bge-reranker 精排**（Query Rewrite+HyDE 已补召回，精排收益最直接）。
- **涉及**：`rag/retriever.py`、`rag/loader.py`、`config/settings.py`。
